# 도담 (Dodam)

> **증상을 확인하면 기록이 되고, 기록이 쌓이면 한 권의 책이 됩니다.**

---

## 1. 서비스 소개

### 한 문장

반려동물의 증상을 공개 수의학 자료를 근거로 **응급 / 병원 권장 / 지켜보기** 로 판단해 주고, 그렇게 확인한 내용이 기록으로 쌓여 **책·굿즈**가 되는 서비스입니다.

### 타겟 사용자

**반려동물의 돌봄을 실제로 전담하는 보호자.** 집에서 아이의 상태를 가장 먼저 알아채는 사람 — 주부와 시니어 보호자가 중심입니다.

| | |
|---|---|
| 상황 | 밤에 아이가 이상해 보여 검색창을 켤 때 |
| 기기 | **스마트폰** (모바일 우선 설계) |
| 심리 | 불안함. 지금 병원에 가야 하는지, 아침까지 기다려도 되는지 모름 |
| 지금 하는 행동 | "3개월 강아지 기침 정상인가요" 검색 → 광고 글과 근거 없는 답변 사이에서 헤맴 |
| 1년 뒤 문제 | 사진은 카메라롤에 흩어지고, 병원에서 *"언제부터 그랬어요?"* 에 답을 못 함 |

### 주요 기능

| 기능 | 설명 |
|---|---|
| **증상 확인** | 증상 19종 + 자유 서술 → 3단계 판정. **판정 근거와 출처 문헌**을 함께 표시 |
| **생활 정보** | 미용 주기·중성화 시기·먹으면 안 되는 것·예방접종·구충·품종 주의사항 |
| **기록** | 확인 결과가 기록으로 저장됨. 사진·체중·메모 직접 작성/수정/삭제 |
| **책 3종** | 성장 스토리북 · 건강수첩 · 추모 앨범 — 기록을 엮어 만듦 |
| **굿즈 3종** | 액자 · 포토달력 · 퍼즐 — 사진 한 장(또는 12장)으로 만듦 |
| **주문 관리** | 주문 생성·조회 + 상태 관리 (`pending → processing → shipped → delivered`) |
| **운영자 화면** | 주문 목록·단계별 집계·상태 전이·CSV 내보내기 |

**외부 API 키가 하나도 필요하지 않습니다.** 지식 베이스 **358건 / 92개 기관**(AVMA·AAHA·WSAVA·ASPCA·ACVIM·ACVS·MSD·Cornell 등)을 저장소에 포함해, 네트워크 없이 전 기능이 동작합니다.

## 2. 실행 방법 (Docker)

```bash
# 저장소 클론
git clone https://github.com/chan-hee1102/sweetbook.git
cd sweetbook

# 실행 — 환경변수 설정이 필요 없습니다
docker compose up

# 접속
# http://localhost:3000
```

> **`.env` 파일을 만들 필요가 없습니다.** 이 앱이 읽는 환경변수는 `PORT`와 `DATA_DIR` 둘뿐이고, 외부 API 키는 하나도 쓰지 않습니다.

### 포트 변경

```bash
PORT=4000 docker compose up          # → http://localhost:4000
```

```powershell
$env:PORT="4000"; docker compose up  # Windows PowerShell
```

또는 `docker-compose.yml`의 `"${PORT:-3000}:3000"` 에서 앞의 `3000`을 직접 수정하셔도 됩니다.

### ⚠️ 심사자께 — 첫 화면에서 「예시 데이터로 둘러보기」를 눌러 주세요

실제 사용자는 자기 반려동물을 등록하는 것으로 시작하므로 **첫 실행은 빈 상태**입니다.
홈의 **「예시 데이터로 둘러보기」** 를 한 번 누르면 **반려동물 3마리 · 기록 49건 · 주문 4건**이 들어가 전 기능을 로그인 없이 확인하실 수 있습니다.

### 5분 둘러보기 순서

1. 홈 → **「예시 데이터로 둘러보기」**
2. **증상 확인 → 몽이 → "숨쉬기 힘들어함"** → 응급(솔리드 빨강) + MSD 수의매뉴얼 근거 + *24시 동물병원 찾기*
3. **초코 → 재채기·털빠짐·몸 긁음 3개** → 병원 권장 (노령견 보정은 걸리되 **응급으로 튀지 않음**)
4. **자유 입력에 "초콜릿을 주워 먹었어요"** → 응급 + ASPCA 근거
5. **자유 입력에 "산책은 얼마나 시켜야 하나요"** → *"이 질문에 답할 자료가 없습니다"* ← 모르는 건 지어내지 않습니다
6. 결과 하단 **「기록에 저장하기」** → 건강수첩 미리보기로 이어짐
7. **책·굿즈 6종** → 담을 내용 고르기 → 주문
8. **내역 → 주문** → 4단계 진행 확인 → 하단 **운영자 화면** → 상태 전이 + CSV

### 데모 상태로 되돌리기

```bash
docker compose down -v && docker compose up
```

또는 **내역 → 주문 → 운영자 화면 → 데모 도구**에서 되돌릴 수 있습니다.

## 3. 완성한 레벨

### ✅ Lv1 — 서비스 구현

- **반려동물 등록** — 이름·종(필수), 태어난 날·성별·품종·체중·중성화·특징·사진(선택)
- **기록 CRUD** — 생성·조회·**수정·삭제**. 종류별 필터, 체중 변화 추이
- **사진 업로드** — 브라우저에서 정사각형 256px JPEG로 줄여 data URL로 저장 (외부 스토리지 없음)
- **증상 확인** — 증상 19종 + 자유 서술 → 3단계 판정 + 근거 문헌 인용
- **생활 정보** — 정보형 질문 6종 + 자유 질문
- 지식 베이스 **358건 / 92개 기관**

### ✅ Lv2 — 자체 주문 기능

- **6종 주문 생성** — 책 3종(성장 스토리북·건강수첩·추모 앨범) + 굿즈 3종(액자·포토달력·퍼즐)
- 담을 기록 선택 → 순서 조정 → 미리보기 → 주문
- **상태 저장·조회·관리**: `pending → processing → shipped → delivered` **단방향 전이를 저장소에서 강제** (되돌리기·건너뛰기 불가)
- **운영자 화면** — 주문 목록, 단계별 집계, 상태 전이
- **CSV 내보내기** (`/api/orders.csv`) — 엑셀 한글 깨짐 방지 BOM 포함

> 결제·배송·회원 인증은 과제 범위가 아니므로 구현하지 않았습니다.
> 다만 **상태는 배송 완료까지** 둡니다 — 보호자에게는 '제작 완료'가 아니라 물건을 받아야 끝이기 때문입니다. 주소를 받거나 택배사를 연동하지는 않습니다.

## 4. 사용자 경험(UI/UX) 설계

### 이 서비스의 과업은 "불안 → 판단"입니다

예쁜 것이 목표가 아니라 **빠르고, 분명하고, 믿을 만한 것**이 목표입니다.

### 판단 1 — 증상 확인이 입구, 기록이 본체, 책이 출구

```
Acquisition          Retention              Revenue
   증상 확인    →       기록 저장      →     책·굿즈 만들기
"기침해요" 검색 유입   확인 결과가 쌓임     1년치를 한 권으로
   [입구]             [본체 = 콘텐츠]        [출구 = 부가기능]
```

과제가 요구한 *"콘텐츠가 본체, 책은 부가 기능"* 구조를 지키면서 **유입 동기**까지 설계에 넣었습니다.
연결고리는 결과 화면의 **「기록에 저장하기」** 버튼 하나입니다. 이게 없으면 확인만 하고 나가서 콘텐츠가 안 쌓이고, 콘텐츠가 없으면 책도 만들 수 없습니다.

### 판단 2 — 한 번에 한 가지만 묻습니다

처음에는 한 화면에 반려동물 선택·증상 19개·자유 입력·결과가 세로로 쌓여 있었습니다.
**급한 사람이 "어디부터 봐야 하지"를 먼저 정해야 하는 화면은 실패한 화면입니다.**

→ **단계 팝업**으로 바꿨습니다.

| 증상 확인 | 책·굿즈 만들기 |
|---|---|
| 1 누구를 확인할까요? | 1 누구의 책인가요? |
| 2 어디가 안 좋나요? | 2 무엇을 담을까요? |
| 3 더 궁금한 것 (선택) | |
| 4 확인 결과 | |

두 흐름의 **조작 방식을 같게** 뒀습니다. 한 번 익히면 다른 쪽에서 다시 배우지 않아도 됩니다.
상태는 전부 URL에 있어서 **뒤로가기가 그대로 '이전 단계'** 가 되고, 자바스크립트 없이 동작합니다.

### 판단 3 — 결과의 위계를 색이 아니라 '무게'로

처음엔 3단계를 모두 `옅은 배경 + 테두리`로 만들고 색만 다르게 했습니다. 그러면 **색맹 사용자에게 응급과 지켜보기가 같은 회색**이고, 정상 시야에서도 얼마나 급한지가 전달되지 않았습니다.

| 단계 | 처리 | 이유 |
|---|---|---|
| 응급 | **솔리드 빨강 + 흰 글씨** | 앱 전체에서 이 화면에만 있는 채도 높은 색면 |
| 병원 권장 | **좌측 4px 선만** | 주의는 주되 화면을 지배하지 않음 |
| 지켜보기 | **흰 배경 + 점 하나** | 안심은 색이 아니라 **색의 부재**로 전달 |

### 판단 4 — 빨간불에서 1순위 행동은 '저장'이 아니라 '병원'

"지금 동물병원으로 가세요"라고 말해 놓고 누를 수 있는 건 저장 버튼뿐이었습니다.
응급·권장 단계에 **병원 찾기 버튼**을 결과 카드 안에 넣고 저장은 그 아래로 내렸습니다.

### 판단 5 — 판정 근거를 반드시 보여줍니다

결과만 던지면 보호자는 그 말을 믿을지 스스로 정할 수 없습니다. 항상 두 가지를 함께 보여줍니다.

- **이 판정에 적용한 규칙** — 어떤 증상/나이/개수가 걸렸는지
- **근거로 삼은 수의학 자료** — 어느 기관의 어떤 문서인지, 원문 링크와 함께

### 판단 6 — 모르는 것은 모른다고 답합니다

자유 질문은 **점수 문턱 + 핵심어 매칭** 두 조건을 모두 넘어야 답변으로 인정하고,
못 넘으면 *"이 질문에 답할 자료가 없습니다"* 라고 말합니다. **그럴듯한 오답이 신뢰를 더 크게 해칩니다.**

### 판단 7 — 나이 있는 사용자를 고려한 조판

- 본문 15px, 제목·버튼은 화면 폭에 따라 커짐 (`clamp`)
- 터치 표적 **최소 44~56px**
- 모든 글자·배경 조합의 명도 대비를 계산해 **WCAG AA(4.5:1) 이상** 보장
- 한글이 음절 중간에서 잘리지 않도록 `word-break: keep-all`
- 폰트(Pretendard)를 **저장소에 포함** — CDN에 의존하면 어떤 PC에서는 다른 굵기로 보입니다

### 판단 8 — 등록을 안내로 끝내지 않습니다

반려동물이 없을 때 *"먼저 등록해 주세요"* 라고 **말하고 끝내지 않습니다.**
그 자리 팝업에서 등록이 끝나고, 등록한 아이가 **곧바로 선택된 채** 다음 단계가 열립니다.

필수 입력은 **이름과 종 둘뿐**입니다 — 밤에 기침 때문에 들어온 사람에게 프로필부터 완성하라고 요구할 수는 없습니다. 다만 **종은 필수**인데, 개와 고양이는 확인하는 증상(위확장염전 vs 요도폐색)과 참고 자료가 다르기 때문입니다.

### 판단 9 — 색의 의미를 하나로 잠갔습니다

초기에는 초록이 4가지(지켜보기·저장성공·주문완료·리셋), 앰버가 5가지 의미를 겸업했습니다. 건강수첩 표에서 **붉은 "병원" 배지와 빨간불이 한 줄에** 놓였고, **체중 숫자가 경고색**이었습니다.

→ **빨강·노랑·초록은 건강 상태 전용으로 잠갔습니다.** 기록 종류는 무채색 + 선 아이콘, 주문 상태는 무채색→브랜드색 농도로 바꿨습니다. 홈 화면 동시 노출 색이 7계열 → 3계열로 줄었습니다.

### 판단 10 — 정상 경로가 아닌 상황

| 상황 | 화면이 하는 말 |
|---|---|
| 제목 없이 저장 | `role="alert"` + 입력란으로 이동 링크 + 자동 포커스 |
| 담을 기록이 없는 기간 | 어떤 종류가 들어가는지 안내, 주문 버튼 비활성 |
| 굿즈인데 사진이 없음 | *"OO은 사진으로 만들기 때문에 사진을 넣은 기록이 한 건은 있어야 합니다"* |
| 자료에 없는 품종 | *"OO 자료는 아직 준비 중입니다. 위 안내는 종·나이 기준이며, 품종별 주의사항은 동물병원에서 확인해 주세요"* |
| 답할 근거가 없는 질문 | *"이 질문에 답할 자료가 없습니다"* |
| 기록이 하나도 없을 때 | *"첫 기록을 저장하세요. 기록이 쌓이면 책으로 만들 수 있습니다"* |
| 없는 주소 | 404 + 홈으로 |
| 검색이 도는 화면 | 스켈레톤 로딩 |

### 의도적으로 넣지 않은 것

| 뺀 것 | 이유 |
|---|---|
| **로그인** | 과제가 "회원 인증은 구현 대상이 아니다"를 명시. 급한 사람이 로그인 화면에서 이탈합니다. 다만 빠뜨린 게 아니라 판단임을 남기려고, 모든 조회가 저장소 함수 6개만 지나가게 짰습니다 — 계정을 붙일 때 `ownerId` 필드와 그 6개 함수의 필터만 추가하면 되고 **화면 코드는 그대로**입니다 |
| **홈의 반려동물 목록 / '기록' 탭** | 매일 켜는 일기장이 아니라 한 번 통과하는 흐름입니다. 목록을 홈에 두면 *"먼저 등록부터 해야 하나?"* 라는 단계가 하나 더 생깁니다. 기록은 진단 저장·책 만들기·내역 세 경로로 도달합니다 |
| **이모지** | 렌더링 주체가 OS라 기기마다 다른 그림이 되고 색·굵기를 앱이 통제할 수 없습니다. 전부 걷어내고 SVG 아이콘(24×24, stroke 1.75)으로 통일했습니다 |
| **인쇄용 PDF 생성** | 과제 FAQ가 불필요하다고 명시했습니다 |

|---|---|---|
| 프레임워크 | **Next.js 14** (App Router) | 서버 컴포넌트 + Server Actions만으로 전 기능 구현. 클라이언트 JS 없이 동작 |
| 언어 | **TypeScript** | 6종 프리셋·4단계 상태 전이처럼 경우의 수가 많은 곳에서 컴파일 타임에 누락을 잡음 |
| 스타일 | **Tailwind CSS** | 빠르되 기본 팔레트는 쓰지 않고 색·크기·모서리를 이 서비스용 토큰으로 재정의 |
| 저장소 | **JSON 파일** | 아래 참고 |
| 폰트 | **Pretendard (self-host)** | CDN 의존 시 환경마다 다른 굵기로 보임. SIL OFL 1.1 포함 |
| 실행 | **Docker (multi-stage)** | `output: "standalone"` 으로 런타임 이미지 최소화 |

### 왜 DB를 쓰지 않았는가

심사자가 **명령 하나로 실행**해야 하는데, DB 컨테이너를 붙이면 실패 지점이 하나 늘어납니다.
데이터 규모(반려동물·기록·주문)가 파일 하나로 충분하고, **원자적 쓰기**(임시 파일 → rename)로 프로세스가 죽어도 파일이 깨지지 않게 했습니다.
다만 모든 접근을 `store.ts` 한 겹에 모아 뒀기 때문에, **DB로 바꿔도 화면 코드는 바뀌지 않습니다.**

### 디렉터리 구조

```
sweetbook/                    # 저장소 루트
├── docker-compose.yml        # PORT 환경변수로 포트 변경
├── Dockerfile                # deps → builder → runner 3단계
├── seed/
│   ├── knowledge.json        # 수의학 지식 358건 / 92개 기관
│   └── demo.json             # 예시 데이터 (반려동물 3 · 기록 49 · 주문 4)
└── src/
    ├── app/                  # 화면 (서버 컴포넌트)
    │   ├── page.tsx          #   홈 — 증상 확인 + 책·굿즈 6종
    │   ├── diagnose/         #   증상 확인 4단계 팝업
    │   ├── books/[type]/     #   책·굿즈 만들기 2단계 팝업
    │   ├── pets/             #   반려동물 · 기록 CRUD
    │   ├── history/          #   내역 (진단)
    │   ├── orders/           #   내역 (주문)
    │   ├── admin/            #   운영자 — 상태 전이
    │   └── api/orders.csv/   #   CSV 내보내기
    ├── components/           # 재사용 UI (아이콘·사진·폼·탭바)
    └── lib/
        ├── triage.ts         # 판정 규칙 엔진
        ├── knowledge.ts      # BM25 검색 + 한국어 2-gram
        ├── ask.ts            # 생활 정보 질의응답
        ├── books.ts          # 6종 프리셋 (책 3 + 굿즈 3)
        ├── store.ts          # JSON 저장소 — 모든 데이터 접근의 유일한 통로
        ├── actions.ts        # Server Actions
        └── josa.ts           # 한국어 조사 처리 (은/는, 이/가, 와/과)
```

### 핵심 설계 — 판정은 규칙이, 근거는 검색이

```
증상 선택 ─┐
          ├─→ [triage.ts]  규칙 엔진 → 응급 / 병원 권장 / 지켜보기
자유 서술 ─┘        │
                   └─→ [knowledge.ts]  BM25 검색 → 근거 문장 + 출처 링크
```

판정을 생성 모델에 맡기면 **같은 증상에 다른 답**이 나옵니다.
판정은 결정적인 규칙이 하고, 검색은 그 판정을 뒷받침할 원문만 찾아옵니다.

노령·다중 증상 보정은 **한 단계까지만** 올립니다(soft cap). 이 장치가 없으면 노령견 + 경증 3개가 응급으로 튀어 **거짓 경보**가 됩니다.

## 6. AI 도구 사용 내역

| AI 도구 | 활용 내용 |
|---|---|
| **Claude Code** (VS Code) | 전체 아키텍처 설계, 프론트엔드·백엔드 구현, 리팩터링, Docker 세팅 |
| **ChatGPT** | 수의학 지식 베이스 초안 수집·정리, 더미 데이터 생성 |
| **대화형 AI** | 모르는 라이브러리·문법 확인 |

### 어떻게 다뤘는가

AI를 **코드 생성기가 아니라 검증 대상**으로 다뤘습니다.

```
설계 판단(사람) → 구현 지시(AI) → 로컬에서 직접 사용 → 원인 규정(사람) → 재지시
```

*"팝업으로 바꿔줘"* 같은 지시로는 원하는 결과가 나오지 않았습니다.
*"급한 사람이 어디부터 볼지 먼저 정해야 하는 화면은 실패한 화면이니 한 번에 한 가지만 묻는 구조로 바꿔라"* 처럼 **이유와 제약을 함께** 줘야 의도대로 나왔습니다.

### AI가 만든 것에서 실제로 나온 문제

문법 오류는 거의 없었습니다. 문제는 **"그럴듯하게 틀리는 것"** 이었습니다.

| 문제 | 발견 경위 |
|---|---|
| 목록 정렬이 오래된 순이라 **세상을 떠난 아이가 기본 선택** — 메인 버튼이 그 아이의 증상 확인을 열었음 | 코드는 정상. 화면을 눌러 보다 발견 |
| 조건이 사실상 항상 참이 되는 CSS로 **화면 전체가 흐릿** | 직접 보다가 "왜 흐릿하지" |
| *"폭에 맞춰 줄어들어 안 잘린다"* 는 주석 — 실제로는 **줄바꿈 대신 화면 밖으로 밀려남** | 모바일 폭 검사 스크립트 |
| 면책은 "진단이 아니다"인데 옆 설명은 "**진단**·병원·접종" — **제품 전체로는 모순** | 문구 전수 점검 |
| *"산책은 얼마나"* 에 중독 문서가 검색됨 | 직접 질문해 보다 발견. **세 번 실패 후** 원인을 규정해 해결 |

**대응**: 눈으로 본 것을 코드로 고정했습니다. 실제로 화면을 띄워 HTTP로 검사하는 스크립트를 **10종 380개** 만들어 수정할 때마다 전부 돌렸습니다 — 마법사 흐름, 상태 전이, 명도 대비(WCAG AA), 모바일 320px 넘침, 이모지 0건, 열린 리다이렉트 차단 등.

**결론**: AI는 **속도**를 주지만 **판단**을 주지 않습니다. 위 문제 중 타입 검사나 문법 검사로 잡히는 건 하나도 없었고, 전부 *"이게 사용자에게 무엇을 의미하는가"* 를 사람이 되물어야 발견됐습니다.

## 7. 설계 의도

### 왜 이 서비스 아이디어를 선택했는가

반려 인구는 빠르게 늘었는데, **반려동물은 아파도 말을 할 수 없습니다.**
보호자가 이상 징후를 발견했을 때 할 수 있는 일은 사실상 검색뿐인데, 결과는 광고와 근거 없는 글이 섞여 있어 정작 *"지금 병원에 가야 하는가"* 라는 단 하나의 질문에는 답을 주지 못합니다.

처음에는 '반려동물 포토북'으로 시작했다가 버렸습니다. 포토북만으로는 **사람이 왜 이 사이트에 처음 들어오는지**에 답할 수 없었기 때문입니다. 책은 추억이 이미 쌓인 다음에야 필요한 물건인데, 그 추억이 어디서 쌓이는지가 비어 있었습니다.

그래서 **유입 동기를 앞에 두고** 구조를 다시 짰습니다.

### 사업적 가능성

- **획득 비용이 낮습니다.** "강아지 기침" 같은 검색 의도는 **이미 존재하는 트래픽**입니다. 수요를 만들 필요가 없습니다.
- **재방문 이유가 구조에 있습니다.** 증상이 생길 때마다 다시 오고, 올 때마다 콘텐츠가 쌓입니다.
- **전환 시점이 자연스럽습니다.** 기록이 쌓인 뒤 책·굿즈를 권하므로, 광고가 아니라 **"이미 만들어진 것을 확인하는" 제안**이 됩니다.
- **인쇄 API와 이해가 일치합니다.** 콘텐츠가 쌓일수록 인쇄 주문이 늘어나는 구조라, 스위트북 같은 인쇄 파트너에게 지속적인 물량이 됩니다.
- **건강수첩은 병원과 연결됩니다.** 진료실에서 실제로 쓰이는 물건이라, B2B(동물병원 제휴)로 확장할 여지가 있습니다.

### 더 시간이 있었다면 추가했을 기능

1. **지식 베이스의 벡터 DB 전환 + RAG** — 지금은 키워드 검색이라 표현이 조금만 달라도 놓칩니다. 임베딩 기반이면 *"숨을 헐떡여요"* 와 *"호흡이 가빠요"* 를 같은 것으로 이해합니다.
2. **사진 기반 증상 분석** — 피부·눈·잇몸 사진을 함께 받아 판단 정확도를 높입니다.
3. **체중·증상 추이 그래프** — 단발 판정이 아니라 *"3주째 계속 기침"* 같은 시간축 패턴을 잡습니다.
4. **동물병원 연동** — 건강수첩을 진료 전 미리 공유합니다.
5. **계정과 다중 보호자** — 가족이 한 아이를 함께 기록합니다. (저장소 구조는 이미 대비해 뒀습니다)
